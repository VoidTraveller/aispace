# AiSpace — сервис бронирования переговорных комнат

Тестовое задание для MSSP Global (KazDream).

## Как запустить

```bash
git clone <repo-url>
cd aispace
cp .env.example .env
# заполнить .env:
#   JWT_SECRET_KEY   — сгенерировать: openssl rand -hex 32
#   DEEPSEEK_API_KEY — выданный ключ
docker compose up --build
```

На Windows (PowerShell, без Git Bash/WSL) команды немного отличаются:

```powershell
git clone <repo-url>
cd aispace
copy .env.example .env
# JWT_SECRET_KEY сгенерировать так:
python -c "import secrets; print(secrets.token_hex(32))"
docker compose up --build
```

Само приложение и `entrypoint.sh` выполняются внутри Linux-контейнера, так
что от ОС хоста (Windows/macOS/Linux) ничего не зависит — нужен только
установленный Docker Desktop.

Приложение доступно на `http://localhost:8000`, документация API — на
`/docs`, проверка живости — `GET /health`.

Контейнер `api` сам дожидается готовности PostgreSQL и применяет миграции
при старте — кроме заполнения `.env` ничего вручную делать не нужно.

Прогнать тесты (32 штуки, против отдельной тестовой БД):

```bash
docker compose run --rm api python -m pytest -v
```

## Что реализовано

- Модель данных (users / rooms / bookings), миграции через Alembic
- Аутентификация по JWT (регистрация/логин)
- CRUD для комнат и броней, три тестовые комнаты создаются автоматически
- Защита от пересечения броней на уровне БД (PostgreSQL `EXCLUDE`-ограничение,
  не только проверка в приложении)
- Веб-интерфейс: просмотр занятости, создание и отмена своих броней,
  управление комнатами, бронирование обычной формой и фразой
- Бронирование фразой на естественном языке через DeepSeek API
  (`POST /bookings/nl`), включая многодневные диапазоны ("с понедельника
  по пятницу")
- Тесты pytest против отдельной тестовой базы данных

## Модель данных

```
users:    id, email (unique), hashed_password, first_name, last_name, created_at
rooms:    id, name, capacity, description, is_active
bookings: id, room_id (FK), user_id (FK), title, start_time, end_time, created_at
```

## Решения, которые стоит пояснить

- **Двойное бронирование блокируется на уровне PostgreSQL**, а не только
  в коде приложения. На `bookings` наложено ограничение
  `EXCLUDE USING gist (room_id WITH =, tsrange(start_time, end_time) WITH &&)`
  — проверка в коде одна не спасает от гонки двух параллельных запросов,
  а ограничение в БД не даст вставить пересекающуюся строку физически.
  Брони встык (одна заканчивается ровно там, где начинается другая)
  разрешены — это нормально для переговорки.
- **JWT вместо серверных сессий** — не нужно общее хранилище сессий,
  токен просто проверяется по подписи. Из-за этого токен нельзя отозвать
  досрочно, поэтому срок жизни ограничен (24 часа по умолчанию).
- **Пароли хешируются напрямую через `bcrypt`**, без `passlib` — его
  bcrypt-бэкенд конфликтует с новыми версиями пакета `bcrypt`.
- **Тесты используют отдельную БД `aispace_test`** с теми же Alembic-миграциями,
  что и продакшн — иначе прогон тестов затирал бы сид-данные в реальной базе.
- **Фронтенд — Jinja2 + vanilla JS**, без SPA. Экранов немного (вход,
  список комнат, две формы бронирования), так что сборка и React/Vue
  были бы избыточны.
- **`POST /bookings/nl` переиспользует ту же функцию проверки конфликтов**,
  что и обычное создание брони — DeepSeek только парсит фразу в структурированные
  поля, дальше всё идёт по одному пути.
- **Многодневные бронирования** ("каждый день с 10 до 15, с понедельника по
  пятницу") создают отдельную бронь на каждый будний день, а не одну
  сплошную бронь на несколько суток — так честнее отражает реальную занятость
  комнаты. Выходные дни в диапазоне пропускаются автоматически, если только
  пользователь не выбрал ровно один день, который сам по себе выходной.
- **Сопоставление комнаты по фразе — через точный список имён в промпте.**
  Изначально DeepSeek возвращал название комнаты в том падеже, в котором
  оно стояло во фразе ("тихую"), а в базе комнаты хранятся в именительном
  ("Тихая комната") — по подстроке не находилось. Решение: передавать в
  промпт список реальных активных комнат и требовать точное совпадение.
- **Ошибки DeepSeek API не роняют сервис** — любой сбой (таймаут, невалидный
  ответ) превращается в `502` с понятным сообщением, а не в 500.
- **Время начала брони в прошлом отклоняется** — для внутреннего инструмента
  бронирования задним числом смысла нет.
- **Таймзоны не учитываются** — сервис для одного офиса, все времена серверные.

## Осознанно не реализовано

Поддержка нескольких офисов (`Building`) — в задании речь об одном офисе,
добавлять эту сущность без реальной необходимости не стал. При надобности
это одна дополнительная миграция (`rooms.building_id`).

## Использование AI-ассистента

Мой основной опыт — Data Analysis и отчасти Data Engineering, на бэкенде
раньше писал на Django, а FastAPI и Alembic осваивал уже по ходу этого проекта.
При разработке использовался Claude Sonnet 5 — в основном там, где не
хватало собственного опыта: во фронтенде (вёрстка, JS), в написании
тестов на pytest и в поиске и исправлении части багов. Архитектурные и
продуктовые решения, бэкенд и работа с БД, нахождение некоторых других багов — моя часть.
