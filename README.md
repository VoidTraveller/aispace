# AiSpace — сервис бронирования переговорных комнат

Тестовое задание для KazDream.

## Как запустить

```bash
git clone <repo-url>
cd aispace
cp .env.example .env
# заполнить .env:
#   JWT_SECRET_KEY   — сгенерировать: openssl rand -hex 32
#   DEEPSEEK_API_KEY — выданный ключ
docker compose up --build
```

Приложение будет доступно на `http://localhost:8000`.
Проверка живости: `GET /health`. Интерактивная документация API (автоматически
от FastAPI): `http://localhost:8000/docs`.

При старте контейнер `api` сам дожидается готовности PostgreSQL и применяет
все миграции — никаких ручных действий, кроме заполнения `.env`, не требуется.

## Что реализовано

- [x] Docker-окружение с автоматическим ожиданием БД и применением миграций
      при старте (`entrypoint.sh`)
- [x] Модель данных (users / rooms / bookings) и миграции через Alembic
- [x] Защита от пересечения бронирований на уровне PostgreSQL (см. ниже)
- [x] Аутентификация (регистрация/логин, JWT)
- [x] API-эндпоинты для комнат и бронирований (`GET /rooms`, `GET /bookings`,
      `POST /bookings`, `DELETE /bookings/{id}`) + автоматическое заполнение
      трёх тестовых комнат при первом старте
- [x] Веб-интерфейс (просмотр занятости, создание брони, отмена своей брони,
      бронирование фразой) — регистрация/вход, карточки комнат и занятости,
      ручная и NL-бронь
- [x] Создание брони фразой на естественном языке (`POST /bookings/nl`,
      DeepSeek API) — переиспользует ту же логику проверки конфликтов, что
      и обычное создание брони
- [x] Тесты (pytest) — 22 теста, изолированная тестовая БД, реальные
      миграции (см. "Что сделано сверх минимума")

## Модель данных

```
users:    id, email (unique), hashed_password, first_name, last_name, created_at
rooms:    id, name, capacity, description, is_active
bookings: id, room_id (FK), user_id (FK), title, start_time, end_time, created_at
```

Подробности и полный SQL — в `docs/ARCHITECTURE.md` (внутренний рабочий
документ, не для внешнего чтения, в репозиторий не включён).

## Принятые решения и почему

Каждый пункт — трактовка неоднозначности задания или решение сверх минимума.

- **Защита от двойного бронирования на двух уровнях.** Помимо проверки на
  уровне приложения (для понятного сообщения об ошибке), на таблицу
  `bookings` наложено PostgreSQL-ограничение
  `EXCLUDE USING gist (room_id WITH =, tsrange(start_time, end_time) WITH &&)`.
  Проверка на уровне приложения одна не закрывает race condition — два
  параллельных запроса могут оба пройти проверку до того, как любой из них
  закоммитится. Ограничение на уровне БД физически не позволяет вставить
  пересекающуюся строку, независимо от гонки запросов. Требует расширения
  `btree_gist` (включается в первой миграции).
  Проверено вручную прямыми SQL-запросами: пересекающаяся бронь (14:30–15:30
  поверх существующей 14:00–15:00) отклоняется с ошибкой
  `conflicting key value violates exclusion constraint`; бронь встык
  (15:00–16:00) — принимается корректно, так как `tsrange` в PostgreSQL по
  умолчанию полуоткрытый (`[start, end)`), что соответствует ожидаемому
  поведению для реального офиса (встречи впритык друг к другу — это норма).
- **Alembic использует переменные из `.env`, а не из `alembic.ini`.**
  `alembic.ini` намеренно оставлен с плейсхолдером; реальный `DATABASE_URL`
  подставляется программно в `alembic/env.py` через `settings` из
  `app/config.py`. Так есть только один источник правды для конфигурации
  и подключения, и исключён риск случайно закоммитить реальные креды в
  `alembic.ini` (в отличие от `.env`, он не в `.gitignore`).
- **Автоматическое применение миграций при старте контейнера**, а не
  вручную. Условие задачи требует запуска без ручных действий, кроме
  заполнения `.env` — поэтому `alembic upgrade head` встроен в
  `entrypoint.sh` контейнера `api`, наравне с ожиданием готовности
  PostgreSQL перед стартом (`depends_on` в docker-compose гарантирует
  только запуск контейнера БД, а не готовность самой PostgreSQL принимать
  соединения).
- **Авторизация через JWT, а не серверные сессии.** JWT не требует общего
  хранилища сессий между запросами — сервер проверяет подпись токена
  (`JWT_SECRET_KEY`) без обращения к БД на каждый запрос, что проще для
  такого масштаба сервиса. Компромисс — токен нельзя отозвать до истечения
  срока действия; для этого задан относительно короткий срок жизни
  (`ACCESS_TOKEN_EXPIRE_MINUTES`, по умолчанию 24 часа).
- **Пароли хешируются через `bcrypt` напрямую, а не через `passlib`.**
  `passlib`'s bcrypt-бэкенд несовместим с текущей версией пакета `bcrypt`
  (обращается к атрибуту `__about__`, удалённому в новых релизах) — известная
  проблема экосистемы. Прямой вызов `bcrypt.hashpw`/`bcrypt.checkpw` проще
  и не зависит от неподдерживаемой прослойки совместимости.
- **Удаление брони — только своей.** `DELETE /bookings/{id}` сначала
  проверяет существование брони (404), затем принадлежность текущему
  пользователю (403) — в этом порядке, чтобы не пытаться сравнивать
  владельца с несуществующей записью. Проверено вручную: пользователь B не
  может удалить бронь пользователя A (403), автор может (204), повторное
  удаление уже удалённой брони — 404.
- **Тесты используют отдельную базу данных (`aispace_test`), а не реальную
  `aispace`.** Изначально `conftest.py` подключался к той же базе, что и
  приложение, и `TRUNCATE` перед каждым тестом стирал реальные данные
  (включая заполненные сидом комнаты) при каждом запуске тестов — неприемлемо
  даже для тестового задания. Исправлено: `conftest.py` при первом запуске
  тестовой сессии сам создаёт `aispace_test` (если её ещё нет) и применяет к
  ней те же самые Alembic-миграции, что и к реальной БД — так схема тестовой
  базы гарантированно идентична продакшн-схеме (включая `EXCLUDE`-ограничение
  и расширение `btree_gist`), а не отдельная, потенциально расходящаяся копия.
  Зависимость `get_db` в приложении переопределяется (`app.dependency_overrides`)
  на сессию к тестовой базе. Проверено вручную: после полного прогона тестов
  сид-данные реальной БД остаются нетронутыми.
- _TODO: фронтенд — почему Jinja2 + vanilla JS, а не SPA-фреймворк_
- **Создание брони через DeepSeek переиспользует `create_booking_or_409`.**
  `POST /bookings/nl` не дублирует логику проверки конфликтов и активности
  комнаты — она парсит фразу через DeepSeek в структурированные поля,
  валидирует их (обязательные поля присутствуют, длительность 1 мин – 8
  часов, дата/время парсятся), определяет комнату, а затем вызывает ту же
  функцию создания брони, что и обычный `POST /bookings`. Сегодняшняя дата
  для разрешения относительных выражений ("завтра") берётся на сервере, а
  не от клиента.
- **Определение комнаты — точный список имён в промпте, а не сопоставление
  подстрок постфактум.** Изначально DeepSeek извлекал произвольное описание
  комнаты, которое сравнивалось через `ILIKE '%query%'` с именами комнат в
  БД. На практике это ломалось из-за русского словоизменения: DeepSeek
  корректно извлекал слово в том падеже, в котором оно стоит во фразе
  («тихую», «большую переговорку» — винительный падеж), а имя комнаты в БД
  хранится в именительном («Тихая комната», «Большая переговорка») — буквы
  не совпадают, и даже пример фразы из самого задания периодически не
  находил комнату. Исправлено: перед вызовом DeepSeek в промпт передаётся
  точный список существующих активных комнат, и модель обязана вернуть
  ровно одно из этих имён (или null). Точное совпадение имени проверяется
  первым; сопоставление по подстроке (`ILIKE`) оставлено как резервный
  вариант. Заодно в промпт добавлено явное разрешение дней недели («в
  пятницу», «на среду») — раньше обрабатывались только относительные
  выражения вроде «завтра».
- **Отказ DeepSeek API обрабатывается явно, не падает в 500.** Любая ошибка
  вызова (таймаут, сетевая ошибка, невалидный JSON в ответе) оборачивается
  в собственное исключение `DeepSeekParseError` и превращается в понятный
  `502 Bad Gateway` с советом создать бронь вручную — семантически 502
  корректен здесь, так как проблема во внешнем сервисе, а не в самом API.
  Покрыто тестом с моком (`test_nl_booking_deepseek_failure_returns_502`) —
  реальный вызов API специально не используется в тестах, чтобы не зависеть
  от сети и не иметь возможность детерминированно вызвать сбой у реального
  сервиса.
- **Допущение по таймзонам: все времена — серверные, без конвертации.**
  Для внутреннего инструмента одного офиса это осознанное упрощение, а не
  недосмотр — сервер и все пользователи находятся в одном часовом поясе.
- **Бронь с временем начала в прошлом отклоняется (422).** Проверка — в
  `create_booking_or_409`, поэтому действует одинаково для ручного создания
  и для `/bookings/nl`. Для внутреннего инструмента бронирования комнат нет
  legitimate-сценария создать бронь «задним числом».
- **Многодневное бронирование в веб-интерфейсе создаёт N отдельных броней
  (по одной в день), а не одну непрерывную бронь через несколько дней.**
  Условие «с 10:00 до 15:00, с 4 по 7 сентября» интерпретировано как
  повторяющийся ежедневный интервал, а не как физическая занятость комнаты
  все ночи между этими датами — что было бы явно неверным поведением для
  переговорной комнаты. Выходные дни (сб/вс) автоматически исключаются из
  диапазона нескольких дней, так как маловероятно, что они входили в
  намерение пользователя. Исключение: если выбран ровно один день и это
  выходной — бронь всё равно создаётся, так как явный выбор одного
  конкретного дня — это осознанное решение пользователя, а не случайное
  попадание выходного в диапазон.

## Что сделано сверх минимума

- Поле `is_active` у комнаты — позволяет временно закрыть комнату для
  бронирования (ремонт, обслуживание) без удаления самой записи.
- Имя и фамилия пользователя (`first_name`, `last_name`) вместо голого
  `user_id` — понятно, кто забронировал комнату, при просмотре занятости.
- PostgreSQL-ограничение `EXCLUDE` как физическая гарантия от двойного
  бронирования (см. выше) — не только проверка на уровне приложения.
- Удаление собственной брони (`DELETE /bookings/{id}`), с проверкой владения
- 22 автотеста (pytest) против реальной изолированной БД — конфликты
  бронирования, некорректный ввод, авторизация, владение бронями, а также
  отказ DeepSeek API через мокирование. Запуск:
  `docker compose run --rm api python -m pytest -v`

## Осознанно не реализовано (scope-decision)

**Сущность `Building` (поддержка нескольких офисов).** Условие задачи
описывает один офис на 60 человек — многоофисность не входит в
сформулированную проблему. Учитывая ограничение по времени, я счёл
рискованным тратить его на архитектуру под нужду, которой нет в условии,
вместо того чтобы довести до полноты обязательный минимум, тесты и это
README. `rooms.building_id` — естественная точка расширения, если это
станет реальным требованием (добавляется одной Alembic-миграцией без
изменения существующих данных).
